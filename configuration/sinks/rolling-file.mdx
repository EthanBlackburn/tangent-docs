---
title: "Rolling file"
description: "Keep records as whole files in a directory, for a query engine to read."
---

The **Rolling file sink** keeps records as whole files in a directory, for a query engine such as DataFusion, DuckDB, or Spark to read. It works the way the [S3 sink](/configuration/sinks/s3) does, with a local directory in place of a bucket. A reader listing the directory sees only whole files.

---

## Schema

<ParamField path="type" type="string" required>
Must be `rolling_file`.
</ParamField>

<ParamField path="path" type="string" required>
The directory the files go in. It can hold strftime specifiers, rendered in UTC when a write reaches the sink, so `lake/logs/%Y/%m/%d/%H` puts each hour's files in a directory of their own, which a query engine can skip by path. A file holds the records written in that hour, whatever times they carry.
</ParamField>

<ParamField path="wal_path" type="string" required>
The WAL's own directory. It can't be another sink's WAL, and it can't be inside `path`, where a reader would find the files the sink stages. Tangent won't start otherwise.
</ParamField>

<ParamField path="max_file_age_seconds" type="int">
Longest time, in seconds, a WAL file stays open before it's sealed and written out. Defaults to `60`.
</ParamField>

<ParamField path="object_max_bytes" type="int">
The size of records at which a WAL file is sealed and written out, whatever its age. Defaults to `134217728` (128 MiB).
</ParamField>

<ParamField path="encoding" type="object">
How records are serialized. See [Encoding](/configuration/sinks/encoding).
</ParamField>

<ParamField path="compression" type="object">
How encoded files are compressed. See [Compression](/configuration/sinks/compression).
</ParamField>

---

## Example

This is the `lake` sink in [packs/core](/packs/overview):

```yaml tangent.yaml icon=upload
sinks:
  lake:
    type: rolling_file
    path: lake/logs/%Y/%m/%d/%H
    wal_path: lake/wal               # apart from path
    max_file_age_seconds: 3600       # a file an hour, unless 128 MiB of records seal it sooner
    compression: { type: zstd, level: 3 }
    encoding:
      type: parquet
      record_column: record
      schema:
        ts: timestamp
        source: string
        _norm: { org: string, actor: string, kind: string, ip: string }
```

---

## Behavior

* A write is acked once it's in the WAL under `wal_path`.
* A WAL file is sealed at `object_max_bytes` of records or `max_file_age_seconds` after it opened. Each sealed file becomes one file in the directory, in the sink's encoding. It's synced and renamed into place, or copied under a hidden temporary name first if the WAL is on another filesystem.
* A file is named the way an S3 object is: `<ULID>.parquet`, or `<ULID>.ndjson.zst` for zstd NDJSON. The ULIDs sort by time.
* The open WAL file is synced only when it's sealed. What was acked survives tangent stopping without its flush (killed, crashed, or out of time at shutdown): the next start seals and writes out the files left open, cut back to their last whole line. It doesn't survive the machine going down before the file is sealed.
* `tangent_sink_bytes_total` counts a file's bytes once it's in place, and `tangent_sink_bytes_uncompressed_total` counts the NDJSON bytes of the records it holds.
